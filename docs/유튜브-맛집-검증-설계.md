# 유튜브 기반 맛집 발굴·검증 시스템 — 1차 분석과 설계

작성: 2026-11-17 · 범위: 분석과 설계만(기존 시스템은 수정하지 않음) · 법률 자문이 아니며 최종 판단은 운영자가 한다.
표기: **[확인]** 공식 문서·코드에서 직접 확인 · **[확실하지 않음]** 근거가 약함 · **[추측]** 설계상 제안값 · **[별도 확인]** 정책상 불분명해서 구현하지 않고 남겨 둠.

---

## 0. 먼저 알아야 할 결론 4가지

1. **"기존 음식점 테이블"은 없다.** 놀픽은 맛집을 저장하지 않고, 장소 상세를 열 때 구글/카카오를 **실시간**으로 불러 5곳을 고른다(`app/js/core/nearby.js`). 그래서 검증 모듈은 "기존 테이블에 붙이는" 게 아니라 **"승인된 맛집 목록"을 새로 만들고, 실시간 결과를 그 목록으로 거르는** 구조가 된다.
2. **백엔드가 없다.** 앱은 정적 웹앱(GitHub Pages)이고, 서버 역할은 하루 한 번 도는 GitHub Actions뿐이다. 그래서 "백엔드 내부 검증"은 **Actions 배치(조건 A, 영업 상태)** + **브라우저 실시간 호출(조건 B 평점)** 로 나뉜다.
3. **조건 B(방문자 평가)는 저장할 수 없는 데이터에 기대야 한다.** 구글 평점·리뷰 수는 약관상 저장 금지(장소 ID만 영구 저장 가능), 네이버·카카오 공식 API에는 평점이 없다. 그래서 **평가 판정은 추천 순간에 실시간으로** 하고, 저장하는 것은 장소 ID뿐이다.
4. **YouTube 약관의 "데이터 집계 금지" 조항이 이 설계의 핵심 쟁점이다.** 여러 채널의 API 데이터를 모아 후보 DB를 만드는 것이 이 조항에 걸리는지 약관만으로는 단정할 수 없다 → **[별도 확인]** 로 남기고, 그 사이에도 진행할 수 있는 **사람이 정리하는 방식(안 A)** 을 함께 설계했다.

## 2. YouTube 이용 가능 여부와 정책 [확인: 공식 문서]

### 2-1. 할당량·비용
출처: https://developers.google.com/youtube/data/determine_quota_cost (2026-11-12 갱신)
- 기본 할당: `search.list` 하루 100회(별도 통), 나머지 하루 10,000유닛. 무료.
- `playlistItems.list` 1유닛, `videos.list` 1유닛, `channels.list` 1유닛, `commentThreads.list` 1유닛, `captions.list` 50유닛.
- **추정 사용량** [추측]: 승인 채널 50개를 매일 점검 = 업로드 목록 50유닛 + 새 영상 상세 약 5유닛. 하루 100유닛 안팎(1%). 최초 1년치 소급 수집도 약 1,000유닛(10%)이라 한 번에 가능. **`search.list`(하루 100회)는 쓰지 않는다.**

### 2-2. 영상 수집 방식
- 채널 ID로 `channels.list`(`contentDetails.relatedPlaylists.uploads`)에서 업로드 목록 ID를 얻고, `playlistItems.list`로 신규 영상만 확인 → `videos.list`로 제목·설명·게시일·채널ID 조회. 공식 허용 방법이며 키만 있으면 된다. 이 방식은 사용자의 "신규 업로드만 확인" 요구와 같다.

### 2-3. 영상 내용(자막)은 공식적으로 못 읽는다 [확인]
- `captions.download`는 **영상을 수정할 권한이 있는 사용자**만 호출 가능(https://developers.google.com/youtube/data/reference/rest/v3/captions/download). 남의 채널 자막은 공식 API로 받을 수 없다. 요청하신 대로 **영상 다운로드·무단 자막 추출·비공식 크롤링은 설계에서 제외**.
- 따라서 자동으로 볼 수 있는 것은 **제목·설명(+공개 댓글)** 뿐이다. "실제로 방문·추천했는가"는 이 정보만으로 완전 자동 판정이 불가능 → **관리자 검수 필요(5장)**.
- 채널 주인에게 자막 접근 권한을 받는 제휴 방식은 가능하나 별도 협의 사항(이번 범위 밖).

### 2-4. 저장·갱신·삭제 [확인]
출처: https://developers.google.com/youtube/terms/developer-policies (III.E)
- 키만으로 얻은 공개 데이터("Non-Authorized Data")는 **최대 30일**만 저장하고, 그 뒤엔 **삭제하거나 새로 받아 갱신**해야 한다. 가능한 한 최신 값과 일치시켜야 한다.
- 설계 반영: 영상 메타데이터는 `fetchedAt`을 두고 **30일 안에 `videos.list`로 갱신**(삭제·비공개 영상이면 즉시 삭제). 영상 ID 50개가 1유닛이라 비용이 거의 없다.

### 2-5. ⚠ 데이터 집계 금지 조항 [별도 확인]
- 약관: "API 데이터를 **집계하지 말 것**. 단, YouTube가 인정한 **같은 콘텐츠 소유자**의 채널 데이터는 예외"("Data Aggregation" 항목, 같은 페이지).
- 우리 설계는 **서로 다른 여러 채널**의 영상 데이터를 모아 음식점별로 묶는다. 이것이 "집계"에 해당하는지 약관 문장만으로는 **단정할 수 없다**(조항의 취지는 YouTube 이용 현황·수익 파악 금지로 읽히지만, 문구는 넓다). → **구현하지 않고 별도 확인 대상.**
- 확인 방법(실행 가능): ① YouTube API 서비스 **감사·할당량 확장 양식**으로 사용 목적을 설명하고 서면 답변을 받는다. ② 답변 전까지는 **안 A(사람이 정리)** 로 운영한다.

## 3. 실제 구현 가능한 데이터 수집 방식 — 두 가지 안

### 안 A. 사람이 정리하는 방식 (정책 위험 가장 낮음, 바로 시작 가능)
- 운영자(또는 관리자)가 승인 채널의 영상을 **직접 보고** 추천 식당을 "승인 목록"에 적는다(식당 이름·지역·**근거 영상 링크**·광고 여부·확인일). 이는 편집 판단이며 API 데이터를 모으는 것이 아니다.
- 자동화는 검증·정리 단계에만 쓴다: 이름 → 카카오 장소 ID 연결, 폐업 확인(공공데이터), 구글 장소 ID 저장.
- 장점: YouTube 집계 조항·30일 저장 조항과 무관. 단점: 사람 손이 든다.

### 안 B. API로 후보를 자동 발굴 (2-5 확인 후에만)
- 승인 채널 신규 영상 → 제목·설명에서 후보 추출 → 자동 식별 → **관리자 검수 큐**에서 최종 확정.
- 단, 확정된 결과에는 **영상 ID만 참조**로 두고, 영상 메타데이터는 30일 갱신·삭제 규칙을 지킨다.
- 2-5에 대한 서면 확인이 오기 전에는 켜지 않는다.

→ **권장: 안 A로 시작하고, 안 B는 확인 결과에 따라 같은 구조에 "후보 입력 경로"만 추가.** 두 안은 아래 DB·판정 로직을 공유한다.

## 4. 신규 데이터베이스 구조 (기존 데이터는 변경하지 않는 별도 모듈)

저장소가 공개이고 앱은 서버가 없으므로 **두 층**으로 나눈다.

### 4-1. 내부 층 `tools/food-verify/` (앱에 배포하지 않음)
| 파일 | 내용 |
|---|---|
| `channels.json` 전문 채널 승인 목록 | channel_id, 채널명, 승인일, 승인 사유, 상태(active/paused) |
| `candidates.json` 영상↔식당 후보 | candidate_id, video_id, channel_id, 영상 제목·게시일(**fetchedAt**, 30일 갱신 대상), 추출된 식당명·지역, 식별 상태(unlinked/ambiguous/linked), **YouTube API 데이터 영역** |
| `restaurants.json` 식당 식별 결과 | place_key(카카오 ID·구글 place_id·전화·주소·좌표·지점명), 식별 방법·신뢰도 |
| `verdicts.json` 검증 결과 | place_key별 조건 A 판정(채널 수, 근거 video_id 목록, 광고 여부, 방문 확인 여부, 검수자·검수일), 영업 상태(공공데이터 확인일), 최종 상태(eligible/rejected/pending), **탈락 사유 코드**, 갱신일·만료일 |
`candidates.json` 안의 YouTube 값과 `verdicts.json`의 **우리가 만든 판정**을 **필드 단위로 분리**해 보관한다(삭제 요구 시 YouTube 값만 지울 수 있게).
※ `tools/` 안의 파일도 공개 저장소에는 보인다. 비공개가 필요하면 저장소 분리나 Actions 아티팩트 사용을 검토(별도 결정).

### 4-2. 앱 층 `app/data/food-eligible.json` (배포되는 최소 파일)
- 내용: **조건 A·영업상태를 통과한 식당의 장소 ID 목록만**(카카오 ID, 구글 place_id). 평점·영상 정보·점수·사유는 넣지 않는다(UI에 노출 안 함, 평점은 약관상 저장 불가).
- 생성: Actions 배치가 `verdicts.json`에서 `eligible`만 뽑아 만든다. 만료일이 지난 항목은 자동 제외.

## 5. 음식점 추출·식별 알고리즘

### 5-1. 후보 추출 (영상 제목·설명 → 식당명·지역)
1. 설명에서 정형 패턴 우선: `📍 상호 / 주소`, `상호 : …`, 지도 링크(카카오 장소 URL의 숫자 ID는 그대로 장소 ID로 사용), 전화번호 `0\d{1,2}-\d{3,4}-\d{4}`.
2. 제목에서 `[지역] 상호` 형태 추출.
3. 한 영상에서 **식당이 여러 곳 나열**된 경우(TOP N, 맛집 리스트)는 "단순 나열"로 표시 → 자동 통과 대상에서 제외(조건 A의 "목록 나열만으로 불통과").
4. 추출이 불확실하면 후보를 만들지 않고 검수 큐로 보낸다. 지어내지 않는다.

### 5-2. 기존 데이터와 동일 장소 확인
- 카카오 키워드 검색(상호 + 지역어)으로 후보 장소를 받고 **일치도**를 계산: 이름 정규화 일치(공백·지점명·괄호 제거; 기존 `tools/lib/names.mjs` 재사용), 주소 시·군·구/동 일치, 전화번호 일치, 좌표 거리, 지점명.
- **자동 연결 조건 [추측]**: 이름 정규화 일치 **AND**(전화 일치 **OR** 주소 동 일치 **OR** 영상 속 장소 ID 일치). 하나라도 부족하면 **`ambiguous` → 관리자 검수**. 동명 지점이 2곳 이상이면 무조건 검수.
- 구글 place_id는 그 장소 좌표 반경 100m 내 이름 일치로 연결해 저장(ID만 영구 저장 가능).

### 5-3. 영업 상태
- 공공데이터 일반음식점 인허가(상호·주소로 매칭)에서 **폐업이면 즉시 탈락**, 확인 불가면 `pending`(통과시키지 않음). 최종 추천 순간에는 구글 `businessStatus`를 실시간으로 한 번 더 확인(저장 안 함).
- [별도 확인] 전국 표준데이터·조회서비스의 이용허락 범위(서울시는 공공누리 1유형 확인).

**조건 A — 전문 채널 추천**
| 코드 | 규칙 | 실패 시 |
|---|---|---|
| A1 | 영상 채널이 승인 목록(active) | `A1_UNAPPROVED_CHANNEL` |
| A2 | 그 영상에서 실제 방문·추천 사실 확인(검수자 확인 또는 단일 식당 영상+규칙). **자동 확정 금지** | `A2_NO_VISIT_EVIDENCE` / `A2_LIST_ONLY` |
| A3 | 광고·협찬 아님. 설명의 "광고·협찬·제공받아·유료 광고 포함" 문구가 있으면 광고로 분류. 검수자가 아니라고 확인하면 해제 | `A3_SPONSORED`(광고 영상만으로는 통과 불가) |
| A4 | **서로 다른 채널** 기준 독립 추천 수를 센다(같은 채널 반복은 1). 최소 기준 N개 [추측: 1] — 기준 올리기는 운영 결정 | `A4_INSUFFICIENT_INDEPENDENT` |
| A5 | 식별이 확실(`linked`) | `ID_AMBIGUOUS` |
**영업 상태**: 폐업 → `STATUS_CLOSED`, 불명 → `STATUS_UNKNOWN`(pending).
**조건 B — 방문자 평가** (추천 순간 브라우저에서 실시간 판정, 7장)
**최종 5곳 선정**: 필수 조건 통과 목록(`food-eligible.json`)으로 **후보 집합을 먼저 거른 뒤**, 기존 놀픽 순위(평점·거리·개인화)를 그대로 적용해 5곳을 고른다. 유튜브 점수·평가 점수를 합산하지 않는다.

**⚠ 결정이 필요한 부분**: 통과 식당이 주변에 5곳 미만일 때 — (가) 5곳 미만만 보여 준다, (나) 기존 방식으로 나머지를 채운다. 사용자 화면은 바꾸지 않는 조건이므로 이 선택이 가장 큰 영향을 준다.

## 7. 방문자 평가 기준 제안 (조건 B)

- **데이터**: 구글 평점·리뷰 수만 공식적으로 사용 가능. 추천 순간 실시간 조회(현재 앱이 이미 이렇게 동작) → **저장하지 않는다.** 장소 ID만 저장.
- **평점·리뷰 수**: 기존 순위가 쓰는 보정 평점(리뷰 20개 분량의 4.0 혼합)을 그대로 쓰면 기준이 일관된다. 제안 임계값 [추측, 보정 필요]: **보정 평점 ≥ 4.2, 리뷰 수 ≥ 100**. 데이터가 없으면(평점 null) 통과 불가.
- **임계값을 "기존 데이터 분포를 분석해" 정하는 방법**: 평점을 저장해 둔 적이 없으므로 현재는 분포를 알 수 없다. 구글 약관상 대량 선조회·저장도 안 되므로, 개발용으로 **소수 지점을 실시간 호출한 뒤 통계값(백분위)만 기록**하는 방식을 제안하나 [별도 확인: 통계값 저장도 파생 콘텐츠에 해당하는지 약관상 불분명]. 확인 전에는 위 제안값을 잠정값으로 쓴다.
- **최근성·부정 평가 비율**: 구글 API는 리뷰를 **관련도 순 최대 5개**만 주므로 전체 분포·부정 비율을 **정확히 산출할 수 없다.** 5개 안에서 "1~2점 비율"과 "최신 리뷰 시각"을 참고 지표로만 쓰고, 5개 미만이거나 최신 리뷰가 1년 넘으면 통과시키지 않는 보수적 규칙을 제안 [추측]. 정확한 부정 비율이 필요하면 구글 외 공식 데이터가 없다.
- 평가 데이터가 부족하면 통과시키지 않는다(요구사항대로). 값을 지어내지 않는다.
- 약관 표기 의무(구글 로고·출처 표기)는 평점을 화면에 보여 줄 때 적용되며 현재 앱은 이미 "Google 지도 기준"으로 안내 중. 이번 작업은 UI를 바꾸지 않는다.

## 8. 자동화가 어려운 부분과 관리자 검수 범위

| 단계 | 자동화 | 사람이 필요한 이유 |
|---|---|---|
| 채널 승인 | ✗ | "전문 맛집 채널" 판단은 운영 결정 |
| 영상 수집 | ✓(안 B 승인 후) | — |
| 후보 추출 | △ 정형 설명만 | 자유 서술·자막 속 식당은 못 읽음 |
| 식당 식별 | △ 확실한 경우만 | 동명 지점·표기 차이는 검수 |
| 실제 방문·추천 확인 | ✗ | 자막을 공식적으로 못 읽음 |
| 광고 판정 | △ 문구 규칙 | 설명에 광고 표기를 안 쓴 협찬은 사람이 판단 |
| 영업 상태 | ✓ | 매칭 실패는 검수 |
| 평가 조건 | ✓(실시간) | — |
검수량은 채널 수·업로드 빈도·식당 수에 따라 달라지며 **현재로서는 알 수 없음**. 승인 채널 수를 정하면 추정 가능.

## 9. 단계별 개발 계획 (이번 1차는 위까지)

1. **확인(코드 변경 없음)**: YouTube API 서비스에 사용 목적 서면 확인(집계 조항·30일 저장), 공공데이터 일반음식점 이용허락 범위, 승인할 전문 채널 목록 확정, 5곳 미만 시 처리 방침.
2. **데이터 틀**: `tools/food-verify/` 스키마·검사 스크립트(`check-food-verify.mjs`)와 `food-eligible.json` 생성기. 비어 있으면 현재 동작과 똑같음.
3. **안 A 운영**: 승인 목록 수기 등록 + 자동 식별·폐업 확인.
4. **앱 연결(UI 변경 없음)**: `findShops`가 `food-eligible.json`으로 후보를 거르고 조건 B를 실시간 적용. 허락·자료가 없으면 기존 순위로 폴백하는 스위치.
5. **안 B(확인 후)**: 채널 신규 영상 수집·후보 큐·30일 갱신·삭제.
6. 단계마다 기존 점검(check-site·check-dupes·check-scoring 등)과 신규 점검 통과 후 배포, 실제 Android 확인.

## 10. 별도 확인 대상 정리
1. YouTube 약관 "데이터 집계 금지"가 여러 채널 후보 DB에 적용되는가 → 서면 확인(안 B의 선결 조건)
2. 영상 ID·파생 판정의 30일 저장 규정 적용 범위
3. 구글 평점 통계값 저장이 파생 콘텐츠에 해당하는지
4. 공공데이터 전국 일반음식점 데이터의 이용허락 범위
5. 공개 저장소에 검증 데이터를 두어도 되는지(비공개 보관 필요 여부)
6. 광고 협찬 표시가 없는 협찬 영상 판정 방법
7. YouTube의 `paidProductPlacementDetails`(유료 광고 포함 표시) 필드로 광고 여부를 확인할 수 있는지 [확실하지 않음: 이번에 문서로 확인하지 못함]
