## 3. 보존해야 할 것과 신규 개발이 닿는 곳

**건드리지 않는다**: 저장소/Pages 구조, `eodigaji.v1` 키와 그 안의 필드, 설치 주소, API 키·환경변수, `scoring.js`의 기존 규칙(가족 구성원별 점수·이동시간·총 검색량 뼈대), 수집기의 기존 단계, 중복 제거(`dedupe.js`)와 검사 3종.

**새로 추가하는 방식(원칙)**
- 신규 사용자 데이터(취향·조회·관심 없음·방문·평가)는 **별도 키 `eodigaji.taste.v1`**(새 키)에 저장. 기존 키는 읽기만 한다.
- 신규 장소 메타데이터(출처·최초 발견일·최근 확인일·확인 여부)는 `spots.json`의 **새 필드를 덧붙이는 방식**(기존 필드 불변)으로 하고, 기존 데이터와 구분되게 `meta.*` 아래에 둔다.
- 신규 외부 API는 `tools/adapters/<이름>.mjs`로 독립 모듈화하고, 실패하면 건너뛰게 한다(수집 전체를 멈추지 않음).
- 새 기능은 `app/js/` 안의 **새 파일**로 만들고, 기존 파일은 연결부만 최소 수정한다.

## 5. 코스 생성(D)의 핵심 제약 [확인/추측]

- 영업시간·휴무일은 현재 데이터에 없다. 한국관광공사 상세정보(`detailIntro2`)에 이용시간·쉬는 날 항목이 있는 것으로 알고 있으나 **[검증 필요]**, 구글 장소 정보는 약관상 저장이 제한된다(앞서 확인).
- 따라서 1차 버전은 "확인된 시간만 반영하고, 없는 곳은 **미확인**으로 표시해 일정에서 영업 시간을 가정하지 않는다"는 원칙으로 만든다. 지시서의 "확인되지 않은 정보는 임의로 생성하지 않는다"와 일치한다.

## 7. 단계별 실행 순서(제안) — 2026-11-17 구현 현황은 HANDOFF.md 하단 "고도화" 절 참고

0. **기기 검수 기반 마련**: Android 실기기 점검표 작성(이 환경은 기기 없음)
1. **E 신뢰도 메타 `meta`** + 화면 표시(가장 작고 다른 기능의 토대) — 수집기 변경은 덧붙이기만
2. **A 발굴 고도화**(분류 5종·작성자 수·게시 시점) — `discover.mjs`는 보존하고 결과 필드만 확장
3. **B 지역 트렌드 점수·지도**(신뢰도 포함)
4. **C 취향·행동 데이터**(새 localStorage 키) + 추천 가산 항
5. **D 코스 생성**(영업시간 미확인 처리 포함)
6. **외부 API Adapter**(승인된 것만 실연동, 나머지 Mock 표기)
7. 단계마다: check-site·check-dupes·check-scoring 실행 → 게시 → 사이트 서비스 워커 버전 확인

## 8. 위험 [확인/추측]

- `spots.json`이 3.4MB이고 계속 커진다. 앱이 전부 받아 메모리에서 계산한다. 새 필드를 더하면 더 커지므로 `meta`는 짧은 키로 하고, 모바일 로딩 시간 측정을 단계마다 한다. [추측: 2~3배가 되면 느려질 수 있음]
- 매일 수집이 이미 길다(과거 실행 15~20분 이상). 신규 단계는 호출 수 상한과 시간 상한을 둔다. 제한시간은 60분.
- 같은 사이트에 여러 세션이 동시에 올리면 충돌한다(실제로 겪음). 올리기 전 항상 최신 `main`을 받아 합친다.
